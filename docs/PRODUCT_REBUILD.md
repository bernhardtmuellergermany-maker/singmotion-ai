## Additive storage change

`20261027_220000_studio_settings` creates only `studio_settings`, containing copy and JSON template fields. It does not change any previous PostgreSQL table or SQLite financial/media data. Its down migration deliberately refuses destructive removal; roll back application code while retaining the added table. The updated Drizzle snapshot and generated Payload types are included.

Draft state continues using the existing `studio_drafts` SQLite table. No new SQLite schema is needed. The new request identifier is included in the source-job identity; existing projects retain their original identities. Old recording-provenance reviews remain readable audit evidence. No task, reservation, credit, project or video is deleted.

## Railway configuration for a later operator-controlled rollout

No Railway setting was changed by this work. Keep the existing persistent volume and all media/databases, Basic Auth, `STAGING_AUTH_ENABLED=true`, `GENERATIONS_ENABLED=false`, disabled live legacy test switches and disabled customer payments. Do not reset the ledgers.

The private operator path uses the existing `CMS_ENABLED`, dedicated `CMS_DATABASE_URL`, strong `PAYLOAD_SECRET`, exact HTTPS `CMS_ORIGIN`, and `BYTEPLUS_STUDIO_ALLOWED_STAFF_IDS`. An approved editor ID can be allowlisted; Super Admin is not required to use Studio. Provisioning remains an administrator action, not open registration. No new operator secret format is introduced.

A functioning private generator also needs the existing strong `BYTEPLUS_STUDIO_OPERATOR_SECRET`, `BYTEPLUS_STUDIO_ENABLED`, supported duration configuration, valid reviewed `studio-live-policy.json`, private BytePlus/R2 credentials, `AUDIO_TEMPO_ENABLED` for the existing 0.9× workflow, and a healthy enabled recovery worker. The implementation does not invent account-specific provider/output policy, change the historical output allowlist, or enable these flags itself. Internal daily/monthly/total budget settings are not required for new private jobs.

Before using CMS-managed templates in a later rollout, back up the existing CMS database and apply the additive migration through the established migration process. Default Studio copy remains available if settings cannot be loaded. Do not run destructive migration rollback.
