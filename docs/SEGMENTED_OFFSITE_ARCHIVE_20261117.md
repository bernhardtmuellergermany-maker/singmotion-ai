# Segmented encrypted offsite archive — offline building block (2026-11-17)

Tracking: #230. Code: `lib/ops/backup-segmented-archive.mjs`.

## Motivation

The read-only Production inventory found 136 local files (~372 MB), 3 SQLite databases,
34 PostgreSQL tables and 399 private R2 objects (~927 MB). The previous synthetic
HiDrive integration limits each fixture and keeps its committed-run index only in
process memory. It cannot be activated against ~1.3 GB of real customer data.

## What this change implements (no Production transfer)

- A pre-existing **immutable, coherent input file** is read through a file descriptor.
  Input remains read-only; ownership, hard-link count, length, inode and timestamps
  are checked during the operation. **It does not make live mutable SQLite or R2
  source files coherent**; the caller must supply native SQLite snapshots, a
  pg_dump archive or a conditionally fetched stable R2 object.
- Default 4 MiB (maximum 8 MiB) plaintext segments. Only one plaintext segment
  exists in memory at a time; no plaintext staging file is generated by this
  library. No single remote body exceeds 8 MiB + envelope overhead.
- Each segment is encrypted with a newly generated AES-256-GCM key and IV.
  The key is RSA-OAEP/SHA-256 wrapped for a 3072-bit-or-better retained public
  recovery key. The authenticated envelope binds the random run and segment ID.
- An Ed25519-signed index records ordinal, ciphertext and plaintext SHA-256,
  lengths and total hash. This signed index is itself **encrypted before upload**,
  so no source filenames or file contents are exposed to the receiver.
- Sender uses `sink.putStream` with known lengths, and only commits after all
  segments and the encrypted manifest were accepted. It never decrypts or
  invokes remote deletion or a restore.
- The independent reader accepts a retained manifest receipt, checks encrypted
  sizes/hashes and the signed index before reconstructing a new, non-existing
  0600 output. A truncated, corrupted or swapped segment fails closed; a partially
  restored file is deleted.
- The library imposes at most 4,096 segments (32 GiB per immutable source file
  at the maximum segment size). This is a *per-file* bound, not a total quota for
  an entire production snapshot.

## Test and evidence policy

`node --test tests/backup-segmented-archive.test.mjs` exercises >8 MiB of
synthetic data through a new write-only sender and an independent download-only
reader; zero-byte files; corrupt/truncated remote data; wrong private key;
destination non-overwrite; immutable source modification; symlink and key limits.
The Production backup CI includes these tests and the existing SQLite, native
PostgreSQL and paginated R2 synthetic disaster-recovery suite.

**Nothing in this PR sends Production data, calls HiDrive, creates a Railway
service, schedules a job or asserts real restoration.** It is a reusable
cryptographic archive primitive, not a complete operational backup.

## Remaining release blockers

1. Integrate a consistent multi-source producer in the Production **application**
   context, using real SQLite online snapshots, read-only PostgreSQL dump and
   complete private R2 pagination/conditional retrieval. Bound total scratch
   storage, total bytes, runtime and network costs; preserve an auditable
   cross-store recovery cutoff.
2. Extend the private HiDrive transport to accept many 4 MiB segments, validate
   each PUT via remote readback and store a **durable committed-run receipt/index**
   that can be reconstructed after receiver loss or restart. Do not rely on the
   in-memory map used by the synthetic fixture or the 1 MiB test-only limit.
3. Establish **independent, durable escrow** of recovery private keys and signing
   verification keys before any real archive is created; test key retrieval
   and signer/key rotation across multiple backup generations. No recovery private
   key may reside on the upload worker.
4. Provision and test reader/writer mTLS identity lifecycle, expiry, renewal and
   revocation, encrypted offsite retention, immutable deletion protection and
   failure alerts. No archive deletion until authorized retention is proved.
5. Only then authorize a bounded private full Production backup and restore the
   actual offsite ciphertext on an isolated host with **no live Stripe, BytePlus
   or R2 credentials**. Verify the Credit ledger, CMS schema, private MP4/range
   access and RPO/RTO against actual data. Keep #230 open until this passes.

The native daily Railway snapshots documented in
`docs/PRODUCTION_CROSS_STORE_RECOVERY_2026-11-16.md` remain in place but do not
prove independent offsite recovery.

## Follow-up: recover HiDrive commit receipt after worker restart

The one-use synthetic HiDrive receiver previously kept its committed run index
only in process memory. `lib/ops/hidrive-committed-reader.mjs` now provides a
**read-only** discovery path from the exact immutable
`sm-<run>-COMMITTED.enc` receipt already written by the existing HiDrive sink.
The receipt contains random IDs and ciphertext hashes, not plaintext names.
It is size- and schema-bounded, rejects duplicate/unknown IDs, and authorizes
GET of receipt-listed ciphertext only. A newly instantiated reader needs no
sender/receiver in-memory map, no directory listing and never issues PUT/DELETE.
Every downloaded ciphertext file is checked against the remote receipt's
recorded size and SHA-256 before the independent recovery function accepts it.

**Trust boundary:** A HiDrive receipt by itself is not an authenticated backup.
The existing separate recovery step MUST verify the encrypted Ed25519-signed
manifest, segment AES-GCM tags and full plaintext integrity. The receipt-reader
uses the worker's existing private OAuth session; it must be hosted behind the
private mTLS reader boundary. **Do not distribute OAuth secrets to the recovery
host.** Tests prove this API against a fake HiDrive store, not actual outage
recovery or remote provider durability. The Production worker remains setup-only.

Still open: integrate the rehydrated index into the permanent private receiver;
operational certificate/key retention, expiry and rotation; actual multi-source
encrypted upload and independent real-data restore. No acceptance flag changes.
