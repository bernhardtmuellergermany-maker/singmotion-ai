# Separately authorized second test (EUR 50 across both)

No deployment or provider request is performed by this change. The original `live_first_test` singleton, task, approvals, audits and its entire outstanding USD reservation remain untouched. HTTP 500 / 50510 grants no refund or budget release. Two additive private SQLite tables hold the second slot and its budget authorization; no original schema/data is reset. A claimed second slot cannot authorize a third task, even after a timeout or crash before receiving its task ID.

1. In Payload as the same authenticated Super Admin who owns the first plan, load the original plan. Select **Prepare separately authorized test #2**, upload a new JPEG/PNG and a new encoded 4–5-second MP3, and prepare offline. Both content hashes must differ from the first inputs. This creates a separate unpriced plan; no R2 or BytePlus calls occur.
2. Save its independently evidenced inclusive USD spending ceiling and generated-duration bound. Unknown taxes/fees stay unknown; a reviewed inclusive total is supported. The EUR 50 permission itself proves neither the provider charge nor a currency rate.
3. Open **EUR 50 total-budget authorization for test #2**. Supply a conservative, evidence-backed upper bound in EUR per USD (`eurPerUsdUpperPpm`: 1,000,000 units = EUR 1 per USD), an explicit FX fee upper bound in microEUR (1,000,000 = EUR 1), dated evidence, and an authorization expiry in ISO UTC (within seven days). No defaults are filled. Evidence must cover final settlement and all applicable conversion/payment fees; a current spot rate alone is not proof. Click the offline approval button. The server records the authenticated reviewer/time and binds the authorization to the original task/full reservation, the second plan and its cost digest.
4. The bound is evaluated exactly with integers: `ceil((ALL outstanding USD reservations + new inclusive USD ceiling) × EUR-per-USD upper bound) + FX fee bound ≤ EUR 50`. The original reservation must still equal its original authorized upper bound. The effective USD cap is the smaller of the configured cumulative cap and the EUR-backed ceiling. SQLite serializes second-slot claiming; cumulative budget checks at reservation and submission enforce that cap. Missing/expired evidence, budget shortage or a changed cost review blocks submission. The panel distinguishes configured USD capacity, EUR-backed capacity, effective remaining USD and unknown actual billing.
5. Separately configure `BYTEPLUS_SECOND_TEST_ENABLED=true` and `BYTEPLUS_SECOND_TEST_PLAN_ID=<new second plan ID>`. Keep `BYTEPLUS_FIRST_TEST_PLAN_ID` bound to the first plan. Keep the existing admin/first-test authorization, signing/R2 credentials and private download gate. Both `BYTEPLUS_LIVE_TEST_MAX_JOB_MICRO_USD` and `BYTEPLUS_LIVE_TEST_MAX_TOTAL_MICRO_USD` must cover the reviewed amounts, with the entire first reservation retained. Changing those USD caps cannot bypass the fixed EUR-50 proof. Keep `DEMO_MODE=true`, `GENERATIONS_ENABLED=false`, `ADMIN_DEMO_ENABLED=false`, `BYTEPLUS_LIVE_TEST_ENABLED=false`, Basic Auth, CSRF and the private volume unchanged.
6. Select first-test output discovery if exact output metadata is not yet known. Confirm **exactly one paid task (test #2)** and click Start once. Use saved status/polling for that second task, then approve its actual exact output host and bounded MP4 policy before secure retrieval/playback/download. A separate submission is never a recovery action. Existing first-task polling remains available by loading its original plan.

The upper-bound evidence is an operator review, not an automated verification of a bank or BytePlus invoice. If it cannot establish sufficient remaining budget, stop. No automatic currency lookup, invented zero fees, reservation release or increase of the EUR limit is provided. Use one Railway replica and the same private persistent ledger. Do not run separate ledgers to obtain more slots.

## Simplified, explicit planning allowance

Load the existing second plan in Payload. Click **Check dated ECB reference — no paid request** to inspect the source/date, then **Accept planning assumptions and reserve within EUR 50 — no paid request**. Acceptance fetches the fixed public ECB daily XML server-side again; stale (over four days), future, malformed or unavailable references block approval. No credentials are sent to ECB. Approval lasts at most 24 hours and never beyond the reference freshness window.

The operator explicitly accepts **twice the rounded-up reference EUR/USD conversion plus EUR 10 reserved for conversion/payment fees** as planning assumptions. These are not verified bank fee limits, tax evidence, or a guarantee of the final invoice. Actual taxes/fees and first-task billing remain unknown. Both full USD reservations count; the independent configured USD caps still apply. This approval neither rewrites nor supplies missing evidence for the existing provider-cost review. The saved audit basis says `planning-allowance`; the documented-settlement-bound form remains available under Advanced.

Then resolve any listed server/cost blockers, select output discovery if needed, and use the existing final one-time paid confirmation and Start button. Budget acceptance itself never submits, uploads to R2 or polls BytePlus. After submission, poll the same task, review its exact output hostname and media policy, then download/validate that result. Never submit again to retrieve output. No first-slot data/reservations are reset.

Implementation checks use mocked ECB, BytePlus and R2 responses. ECB access from this development environment returned HTTP 403; runtime availability in Railway is not verified. Failure there remains explicit and closed rather than using an invented rate. Application spending limits cannot enforce an external bank/provider invoice ceiling.
