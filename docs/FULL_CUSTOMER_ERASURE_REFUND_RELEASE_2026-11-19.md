# Full customer self-service erasure: release requirements (19 November 2026)

## User-approved target
A single, independently usable **Delete account** button under `Account Settings → Privacy & deletion`, followed by fresh password confirmation (or equivalent fresh Google sign-in), explicit irreversible confirmation, automatic refund of **unspent purchased** Credit value to the original Stripe payment method, and verified removal of the user's accounts, projects and media. No discretionary admin approval. Genuine legal/financial retention must remain segregated. This is a target, **not the present feature**.

## What is implemented in this draft PR
- `customer-erasure-refund-quote.ts`: deterministic, read-only refund plan from Stripe-bound purchases plus the wallet ledger. Ignores gifted Credits; defaults to refusing unreconciled ledger values, active holds, pending Checkout and disputed or reversed credit payments.
- `customer-erasure-refund-intents.ts`: durable original-purchase, customer-bound partial-refund intents; validates the original paid Stripe Checkout, currency, amount and mode. Records intent before external POST; uses a stable purchase-scoped idempotency key and recovery via real Stripe refunds rather than blindly repeating an uncertain POST.
- Isolated regression tests, TypeScript and CI. **No UI change and no refunds initiated** by draft modules.

## Required before wiring this to a LIVE button
1. **Freeze before payout:** A durable, owner-authenticated erasure request must stop logins and all new top-ups, media uploads, provider task submissions, studio actions and wallet debits across every device. Revoke old sessions or restrict them to erasure status. Every fulfillment and provider worker must honor this state.
2. **Real financial reconciliation:** Re-verify the immutable Credit snapshot after freezing; match each charged original Checkout. The refund scheduler must handle insufficient Stripe balance, pending/failed refunds, cards and alternative payment methods, customer-balance payouts, already refunded payments, disputes and previously spent Credits. Never send a second payout when a Stripe response is uncertain.
3. **Stripe webhook handling:** Existing `/api/stripe-webhook` assumes Credit refunds are **full**. A partial erasure refund would currently fail or be mis-reconciled. Implement signed, independently checked erasure-specific partial-refund recognition, exactly-once state transitions, and corresponding invoice/credit note and tax handling before enabling real refunds.
4. **Owner media graph:** Inventory `demo.sqlite`, `live-test.sqlite`, `commerce.sqlite` and related PostgreSQL data, existing paid/guest order claims, active BytePlus jobs, source images/audio, generated MP4 and video previews. Do not delete an active/uncertain job or a shared asset. The current 30-day project trash cleanup is distinct and is disabled in Production.
5. **Cloud deletion:** Remove exact owner-bound `cloud_source_media` records from R2 using verifiable Delete+Head; separately remove `live_input_deliveries` and `customer_provider_input_leases` R2 keys only after their signed input URL expiry/grace and validated provider states. Never delete a bucket by prefix alone. Verify every local file path and avoid symlink attacks. Preserve incomplete manifest for retry.
6. **Cross-store transaction saga:** External refunds and R2 deletes cannot participate in one SQLite transaction. Implement a resumable durable state machine with independent write locks, idempotent step checkpoints, strict recovery, timeouts, bounded retries, observability and a user-visible `Processing / Refunding / Removing files / Completed / Needs attention` status. Only say `deleted` after positive verification, never simply after request submission.
7. **Privacy & retention:** Remove PII from customer login, projects, emails, notifications, events and files without destroying legally retained payment and dispute evidence. Verify with tax/accounting that Stripe + immutable invoice export is a compliant archive; the app must retain any required minimal data pseudonymously and disclose this accurately.
8. **Provider and backup expiry:** Verify BytePlus provider-side deletion/retention contract, R2 versioning/lifecycle, Railway/offsite encrypted backup expiration and signed tombstones applied after restores. Full immediate erasure from immutable historical backup generations is not guaranteed by a live SQL DELETE.
9. **Google-only:** Authenticate an OAuth-only account freshly at deletion with a bounded, nonce/audience/issuer-validated Google flow; no nonexistent password.
10. **Safety release:** Full integration in isolated Staging with mocked and signed Stripe events, sandbox partial refunds and post-refund webhook replay, active provider tasks and media with private R2 objects, customer/guest cross-isolation, crash/retry/failure injection and post-restore erasure verification. Do not use real customer or live monetary data in tests; deploy identical tested commit to Production only after all checks.

## Operational rule
The existing Production version `88e0d0cd5a523e54cb80ce9d68dc7673630e6875` contains limited, verified **empty-account** deletion and deliberately refuses existing paid/media records. This draft PR is not merged, deployed or enabled; do not tell customers partial payouts or full-media self-erasure are already available.
